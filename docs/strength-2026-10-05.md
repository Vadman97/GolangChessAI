## Third deployment: transposition-table mate distances

Found a deterministic mate-score normalization bug. A score of `WinScore+2`
at search depth five represents a mate three plies away. Storage subtracts
five, producing `WinScore-3` (999999997). The old read code recognized only
scores at or above WinScore, so it failed to restore the score when the same
position was reused at another search depth. Losing mate scores had the
corresponding problem above LossScore. This breaks mate-distance comparisons
across cached searches.

Both normalization directions now recognize the reserved mate-score band and
preserve search sentinels. The new regressions fail against the original source
and pass with the correction, covering both signs, several read depths,
ordinary evaluation scores, and sentinels. Existing mate, promotion, repetition,
and root tests passed; focused race tests and server/analysis/board tests passed.
Eight mate/endgame corpus positions at fixed depth four had identical
cold-hash Stockfish depth-18 losses before and after; one selected move changed.
These checks establish a cache correctness fix, not an Elo estimate.

## Root-window probe and capture-ordering bug

An isolated candidate held parallel sibling scout windows fixed at the first
root move's score instead of tightening them as worker results arrived.
In game-12 ply-26, ten 1.2-second searches then selected weak `...c5` every
time; the deployed control selected sound `...d6` six times and `...c5` four.
Every result reported depth seven. The candidate is rejected and its source
change was removed; the live engine retains dynamic sibling windows.
Results and binary identities are preserved in
`testdata/strength_2026_10_05_root_window_probe.json`.
Fresh depth-seven full-window serial searches scored `...d6` -167 and
`...c5` -176, preferring the sound move. Without late-move reductions, the
scores changed to -171 and -162, reversing that ordering. Root ranking is
therefore sensitive to selective-search and cache context as well as arrival
order; making windows deterministic alone did not improve the move.

A separate deterministic move-ordering defect was found in `Board.GetAllMoves`:
the sort compared a fixed precomputed score slice but permuted only the move
slice. In legal FEN `4k3/6q1/7P/3b4/8/8/1B6/3RK3 w - - 0 1`, it placed
`Rxd5` before the higher-value queen captures `hxg7` and `Bxg7`. The correction
swaps scores with moves and preserves generation order among equal scores.
The new regression fails on the original ordering and passes the correction;
it covers cached and uncached generation, repeated calls, and preservation of
the original unsorted move list. Board tests and focused king/ordering race
tests pass. The candidate is built at `/tmp/chess-move-order-fixed`; strength
comparison completed at 1.2 seconds, four workers, three repetitions, and
the same 21 positions. Common cold-hash Stockfish depth-18 mean loss changed

two worsened. The largest improvement recovered `...Be7` in local game-10
ply-34 (76 to 0 cp); the largest regression repeated the known variable
`...d6`/`...c5` choice in game-12 ply-26 (0 to 173 cp). This is mixed evidence,
not a strength claim. Records and binary identities are preserved in
`testdata/strength_2026_10_05_ordering_probe.json`.

The broader 94-position comparison completed at 1.2 seconds, four workers,
